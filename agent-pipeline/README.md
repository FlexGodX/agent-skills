# agent-pipeline

Скилл для AI-агентов (Claude Code и совместимых): превращает работу над задачей
разработки в цикл из 11 этапов, где на четырёх контрольных точках («воротах»)
результат принимает **один независимый агент-ревьюер с чистым контекстом**, а не
сам автор.

Зачем: агент, которому сказали «сделай к вечеру, не усложняй», пропускает
спецификацию и план, а ревью зовёт в конце — или не зовёт. Этот скилл делает
ревью обязательным, ограничивает его по стоимости и не даёт ему бесконечно
расширять задачу.

## Установка

```bash
# Claude Code, глобально
cp -R agent-pipeline ~/.claude/skills/

# или через общий каталог агентов
cp -R agent-pipeline ~/.agents/skills/ && ln -s ../../.agents/skills/agent-pipeline ~/.claude/skills/agent-pipeline

# проектно
cp -R agent-pipeline .agents/skills/
```

### Установка агентом по ссылке

Дайте агенту ссылку на репозиторий и попросите установить скилл
`agent-pipeline`. Ему достаточно выполнить:

```bash
git clone --depth 1 https://github.com/FlexGodX/agent-skills.git /tmp/agent-skills
mkdir -p ~/.agents/skills ~/.claude/skills
rm -rf ~/.agents/skills/agent-pipeline
cp -R /tmp/agent-skills/agent-pipeline ~/.agents/skills/
ln -sfn ../../.agents/skills/agent-pipeline ~/.claude/skills/agent-pipeline
python3 ~/.agents/skills/agent-pipeline/scripts/test_check_artifacts.py
```

Последняя команда проверяет, что скрипт проверки документов работает на этой
машине: все тесты должны пройти. Папка копируется целиком — `SKILL.md`,
`references/` и `scripts/` нужны вместе. Скрипту нужен только Python 3.8+,
сторонних пакетов нет. Чтобы обновить скилл, повторите те же команды.

Скилл **не работает по умолчанию**: он дорогой, от пяти запусков субагентов
на самой маленькой задаче. Он включается в двух случаях:

- вы прямо попросили: «по пайплайну», «полный цикл», «запусти пайплайн»,
  `/agent-pipeline`;
- задача рискованная — меняется схема БД, публичный API, данные между
  клиентом и сервером, авторизация или секреты. Тогда агент не запускает
  пайплайн, а одной строкой предлагает его и без вашего «да» работает обычным
  способом.

Это задаёт поле `description` в `SKILL.md` и раздел «Когда включаться».
Хотите, чтобы скилл срабатывал чаще или реже, — правьте их.

## Цикл

| # | Этап | Результат | Условие перехода |
|---|------|-----------|------------------|
| 1 | Контекст | раздел «Контекст» в `SPEC.md` | блокирующие вопросы закрыты |
| 2 | Исследование | варианты решения, соседние случаи | вариант выбран |
| 3 | Спецификация | `SPEC.md` | **ворота** |
| 4 | Архитектура | `DESIGN.md` | **ворота** |
| 5 | Описание тестов | `QA.md` | на каждый критерий приёмки есть тест-кейс |
| 6 | План | `PLAN.md` | **ворота** (план, тесты, трассируемость) |
| 7 | TODOs | список задач | один TODO на шаг плана |
| 8 | Имплементация | код и тесты | все TODO закрыты |
| 9 | Тестирование | раздел «Прогон» | у каждого тест-кейса результат, нет `FAIL` |
| 10 | Ревью кода | вердикт | **ворота** |
| 11 | Исправления или merge | — | условия готовности |

Артефакты лежат в `docs/pipeline/<тег>-<номер>-<кратко>/`. Критерии приёмки (`AC-NN`),
тест-кейсы (`TC-NN`) и дефекты (`DEF-NN`) связаны сквозной трассируемостью.

## Масштаб задачи

| Размер | Признаки | Ревью |
|--------|----------|-------|
| **S** | один файл и его тест, нет признаков L | 2: одно до кода (вместо ворот 3, 4, 6) и ворота 10 |
| **M** | всё остальное | 4: по одному на каждых воротах |
| **L** | схема БД или миграция; контракт публичного API; формат или состав синхронизируемых данных; логика прав или секретов; новая подсистема | 4, плюс человек утверждает `SPEC.md` и `DESIGN.md` после ворот 4, до кода |

Исправление, после которого уходят те же поля с правильным значением, — не L.
Сомневаешься между размерами — бери больший; срочность размер не уменьшает.

## Ключевые правила

- **Один ревьюер на ворота.** Отдельный субагент с чистым контекстом получает
  артефакт, документы и критерии, но не историю чата, не рассуждения автора и не
  журнал `REVIEW.md`. Заменить его другим способом проверки может только
  пользователь.
- **Вердикт строгий:** `APPROVED` или `CHANGES_REQUESTED` со списком дефектов.
  Дефект закрывает ревьюер следующего раунда, а не слово автора.
- **Возражение автора** передаётся следующему ревьюеру вместе с текстом дефекта;
  отдельного арбитра нет.
- **Соседние случаи.** Автор на этапе 2 и ревьюер на каждых воротах ищут тот же
  дефект в других формах. Молчание документа о таком случае — дефект. Объём
  задачи расширяет только пользователь: остальное уходит в «Не входит в задачу».
- **Ломающие входы.** Ревьюер обязан подобрать вход, на котором решение
  ошибается, или назвать не меньше трёх проверенных. На ревью кода такой вход на
  пути правки — дефект.
- **До кода ломающий вход — это тест, а не блокирующий дефект.** Пока решение
  описано словами, на каждое уточнение находится новый контрпример; закончить
  спор могут только код и тесты.
- **Повторный раунд** считает новым дефектом только три вещи: прошлый дефект не
  устранён, исправление внесло ошибку, нарушен записанный критерий приёмки.
- **Предел:** три раунда подряд на одних воротах без `APPROVED` — решение за
  пользователем.
- **Условия готовности** одни для слова «готово» и для merge: у каждого тест-кейса `PASS` либо `НЕ ЗАПУЩЕН`,
  который пользователь явно принял (пропущенный тест — `НЕ ЗАПУЩЕН`), ревью кода `APPROVED` и код после него не
  менялся, артефакты одобрены, открытых дефектов нет.

## Структура

```text
agent-pipeline/
├── SKILL.md                      # цикл, масштаб, правила ревью, этапы, красные флаги
├── references/
│   ├── artifacts.md              # что внутри SPEC / DESIGN / QA / PLAN / REVIEW
│   ├── phase-prompts.md          # шаблоны запросов исполнителям фаз
│   └── review-prompts.md         # готовые запросы ревьюеру для каждых ворот
└── scripts/
    ├── check_artifacts.py        # программная проверка документов перед воротами
    └── test_check_artifacts.py   # тесты скрипта
```

## Скрипт проверки документов

Перед каждыми воротами оркестратор запускает:

```bash
python3 scripts/check_artifacts.py docs/pipeline/perf-3-web-load --gate 6
```

Ворота: `3`, `4`, `6`, `10` и `s` (ревью до кода при размере S). Скрипт
проверяет то, для чего не нужно суждение: шапки и обязательные разделы,
статусы входящих документов, трассируемость «критерий → тест → шаг плана»,
таблицы «Входы из ревью», «Прогон» и «Мутации». Ответ — строка итога (`OK …`
или `НЕ ПРОЙДЕНО …`) и по строке на ошибку; код возврата 0 или 1. Так
ревьюер не тратит токены на механику, а случай «запущена треть тестов»
ловится до ревью. Смысл требований скрипт не проверяет и ревьюера не
заменяет.

## Происхождение

Собран из двух источников: заметок автора о цикле из 11 этапов с ревью
«по общему правилу» (агент-критик, судьи, человек или программная проверка) и
скилла [autonomous-agentic-development-cycle](../autonomous-agentic-development-cycle/)
(чистый контекст ревьюеров, вердикты, единогласие, трассируемость QA ↔ план).
Проектная специфика исходного скилла убрана, судьи и арбитр заменены одним
ревьюером, добавлены масштаб, соседние случаи и ломающие входы.

## Как проверялось

Скилл прошёл пять полевых прогонов на одной реальной задаче — баг «висящее "к"»
в парсере смарт-инбокса (`Сдать отчёт к пятнице` → заголовок `Сдать отчёт к`).
Агент и ревьюеры работали на модели Sonnet, решение проверялось запуском тестов.

| Версия скилла | Запусков ревьюера | Итог |
|---|---|---|
| с судьями и широким признаком L | 31, около 45 минут | хорошее исправление, непомерно дорого |
| облегчённая, без поиска соседних случаев | 2 | исправление узкое, портило заголовки |
| один ревьюер, проверки без границ | 3 раунда, дважды | не сошлось, до кода не дошло |
| **финальная** | **2** | **рабочее исправление, ревью кода `APPROVED`** |

В финальном прогоне ревью до кода нашло форму «ко вторнику», которую автор
пропустил, а исправление заодно устранило старую порчу заголовков
(`Позавтракать завтра` → `По кать завтра`).

## Ограничения

- Проверено на одной задаче одного типа (текстовый парсер). Размеры M и L
  рассчитаны по тексту скилла, на задачах не запускались.
- Этап 1 (разговор с пользователем) в прогонах не проверялся: пользователь был
  объявлен недоступным.
- После последнего полного прогона в текст внесены правки по ревью самого
  скилла; проверен только изменённый шаблон ревью кода.
- Известный огрех проверенного исправления: одиночная заглавная «К» в
  `Купить витамин К завтра` принимается за предлог.
- Скилл тяжёлый для однострочных правок: для них есть размер S, но процесс всё
  равно требует документа и двух ревью.

## Что изменилось в версии с оркестратором

- Агент, который загрузил скилл, — оркестратор: говорит с пользователем, ведёт
  статусы и решает, куда возвращаться. Код он не читает и не пишет.
- Под каждую фазу запускается субагент с чистым контекстом. Запросы собираются
  из шаблонов в `references/phase-prompts.md`.
- Обмен между фазами идёт через файлы. Исполнитель отвечает коротким отчётом со
  статусом `ГОТОВО`, `БЛОКЕР` или `РАСХОЖДЕНИЕ`.
- Независимые шаги плана (пустая колонка «Зависит от») идут параллельно; шаги,
  которые правят один файл, отдаются одному исполнителю.
- У задачи есть идентификатор `<ТЕГ>-<номер>` (например, `PERF-3`). Он стоит в
  имени папки и в строке реестра `docs/pipeline/INDEX.md`.
- При размере L человек утверждает `SPEC.md` и `DESIGN.md` после ворот 4, до
  начала кода.
- При размерах M и L тестировщик проверяет тесты мутацией: ломает строку,
  которая реализует критерий, и смотрит, упадёт ли тест.
- Уроки из ревью записываются в журнал ошибок проекта (если проект требует
  одобрения пользователя — после него) и в память.
- Размер S — не меньше пяти запусков субагентов: разведчик, автор, ревью до
  кода (один раунд), исполнитель и ревьюер ворот 10.
- Версия с оркестратором проверена одним полевым прогоном на задаче размера
  S. На размерах M и L в реальной работе она пока не запускалась; раздел «Как
  проверялось» описывает прогоны прежней версии.
