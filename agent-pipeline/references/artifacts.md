# Содержимое артефактов

Файлы лежат в `docs/pipeline/<тег>-<номер>-<кратко>/`, если инструкции проекта
не задают другое место. Каждый артефакт (`SPEC.md`, `DESIGN.md`, `QA.md`,
`PLAN.md`; журнал `REVIEW.md` — не артефакт) начинается с шапки:

```text
Задача: PERF-3
Ревизия: 1
Статус: DRAFT
```

«Задача» — идентификатор `<ТЕГ>-<номер>`; его назначает оркестратор, он один
на все файлы папки. Ссылка на критерий другой задачи пишется с ним:
`PERF-3/AC-02`.

Статус после ворот — `APPROVED (ревьюер, ревизия 1)`; для размера L до решения
человека — `APPROVED (ревьюер, ревизия 1); ждёт человека`, после —
`APPROVED (ревьюер и человек, ревизия 1)`. При L человек утверждает
`SPEC.md` и `DESIGN.md`.

Сквозные идентификаторы: `AC-NN` — критерий приёмки, `TC-NN` — тест-кейс,
`DEF-NN` — дефект из ревью. Номера `AC` и `TC` не переиспользуются; `DEF`
нумеруется внутри раунда, в журнале и запросах — с номером раунда:
`Р2-DEF-01`, для ревью S до кода — `S-DEF-01`. Пути и команды в
таблицах ниже — примеры формата.

## Кто что пишет

| Файл или раздел | Пишет |
|-----------------|-------|
| `SPEC.md`: шапка, просьба и ответы пользователя в «Контексте», «Размер»; допущения по `БЛОКЕР` в «Открытых вопросах»; строки «Не входит в задачу» по замечаниям ревью, которые не взяли | оркестратор |
| `SPEC.md`: подраздел «Что найдено» в «Контексте» | разведчик |
| `SPEC.md`: остальные разделы | автор спецификации (при S — автор S) |
| `SPEC.md`: таблица «Входы из ревью» | вход и ожидаемый результат — оркестратор, дословно из вердикта; номер `TC` или причину — планировщик (при S — автор S) |
| `DESIGN.md` | архитектор |
| `QA.md` без «Прогона», `PLAN.md` | планировщик |
| раздел «Прогон» и таблица «Мутации» | тестировщик (при S — исполнитель S, без «Мутаций») |
| раздел «Ход работ» | оркестратор (при S — исполнитель S) |
| статус в шапке, `REVIEW.md` | оркестратор |

Исполнитель оставляет в шапке `Статус: DRAFT`; `APPROVED` ставит оркестратор
по вердикту ворот. Кто изменил содержание документа со статусом `APPROVED`,
поднимает «Ревизия» на 1 и возвращает `DRAFT`. Ревизию не поднимают: «Прогон»,
«Ход работ», строки таблицы «Входы из ревью» и добавленные под них `TC`, шаги
плана и строки «Не входит в задачу».

## Признаки размера

- **L** — меняется хотя бы одно: схема БД или миграция; контракт публичного
  API (эндпоинты, поля, типы, коды ошибок); формат или состав данных,
  которые синхронизируются или передаются между клиентом и сервером; логика
  авторизации, прав или работы с секретами; новая подсистема. Другие
  значения в существующих полях — не L.
- **S** — меняется один файл и его тест либо только тест, нет признаков L, пользователь не
  заметит ничего, кроме исправленного дефекта. Число вызывающих мест размер
  не меняет.
- **M** — всё остальное.

## SPEC.md — что должно получиться

| Раздел | Содержание |
|--------|------------|
| Контекст | просьба пользователя дословно; его ответы дословно; ограничения проекта и найденное в памяти; подраздел «Что найдено» — файлы и функции с номерами строк и вызывающими местами, как это работает сейчас, правила и ловушки проекта, команды тестов, вопросы без ответа в коде |
| Размер | S, M или L и какие признаки выполняются |
| Варианты и выбор | рассмотренные решения, оценка по одним критериям, выбранный вариант, причина отказа от остальных; входы, на которых проверялась хрупкость выбранного способа |
| Соседние случаи | таблица: случай → входит или не входит → причина; у вошедших — номер `AC` |
| Требования | наблюдаемое поведение, без описания реализации |
| Критерии приёмки | список `AC-NN`; каждый проверяем тестом и однозначен |
| Не входит в задачу | что сознательно не делается, включая соседние случаи, оставленные за рамками |
| Входы из ревью | таблица: ломающий вход от ревьюера до кода → ожидаемый результат → номер `TC` либо причина, почему не входит |
| Открытые вопросы | допущения без ответа пользователя с пометкой «не подтверждено» и тем, как каждое влияет на решение |

**Размер S.** `DESIGN.md`, `QA.md` и `PLAN.md` не создаются. Их содержимое —
разделы того же `SPEC.md`: «Решение», «Тесты», «План», «Ход работ», а после
этапа 9 — «Прогон». Где скилл и шаблоны называют эти файлы, для S читай:
соответствующий раздел `SPEC.md`. До ревью раздел «Прогон»
пуст. Статус `APPROVED` при S ставится по вердикту ворот 10; до них документ
остаётся `DRAFT`.

## DESIGN.md — как это встраивается в систему

| Раздел | Содержание |
|--------|------------|
| Затронутые модули | файлы и слои, которые меняются, и кто их вызывает |
| Данные | изменения схемы, миграции, формат хранения, совместимость со старыми данными |
| Интерфейсы | новые и изменённые API, сигнатуры, события, контракты |
| Поведение при ошибках | отказы, гонки, повторы, потеря связи, граничные значения |
| Безопасность | кто имеет доступ, откуда берётся идентичность, что проверяется |
| Решения | каждое значимое решение со ссылкой на свой `AC` и отвергнутой альтернативой |
| Диаграммы | при M и L — в mermaid: последовательность вызовов изменяемого сценария и поток данных; при L ещё затронутые модули и их связи. Только то, что меняется |

Раздел, которого задача не касается, остаётся с пометкой «не затрагивается» и
одной фразой почему.

## QA.md — как проверяем

| TC | AC | Тип | Команда или шаги | Ожидаемый результат |
|----|----|-----|------------------|---------------------|
| TC-01 | AC-01 | unit | `<команда запуска одного теста>` | «Сдать отчёт к пятнице» → заголовок «Сдать отчёт» |
| TC-02 | AC-01 | unit | тот же файл | «Сходить к врачу завтра» → «Сходить к врачу»: предлог не у даты сохраняется |
| TC-03 | AC-02 | ручной | 1) открыть экран… 2) ввести… | в списке одна запись с датой |

На каждый `AC` минимум один `TC`; негативные и граничные случаи — отдельными
`TC`; ручной тест описан шагами, которые повторит другой человек. Имя теста в
коде начинается с номера `TC`, чтобы его можно было запустить отдельно.

Раздел «Прогон» заполняется на этапе 9 и обновляется целиком после каждого
исправления:

| TC | Команда | Результат | Дата |
|----|---------|-----------|------|
| TC-01 | `<команда>` | PASS | 2026-11-24 |
| TC-07 | интеграционный, нужна тестовая БД | НЕ ЗАПУЩЕН: адрес БД не задан | 2026-11-24 |

Последней строкой — прогон тестов кода, который вызывает изменённый.

В колонке «Результат» — только итог после правки: `PASS`, `FAIL` или
`НЕ ЗАПУЩЕН: причина`. Результат до правки сюда не пишется: скрипт проверки
прочитает слово `FAIL` как упавший тест. То, что тест падал до правки,
исполнитель сообщает в своём отчёте.

При M и L под «Прогоном» — таблица «Мутации»: тестировщик ломает строку,
реализующую `AC`, и смотрит, упал ли тест.

| AC | Что сломано | Упавший TC |
|----|-------------|------------|
| AC-01 | `<путь>:42` — `>` заменён на `<` | TC-02 |
| AC-03 | `<путь>:77` — убрана ветка | НИ ОДИН |

«НИ ОДИН» значит, что тесты этот дефект не ловят: это то же, что `FAIL`.
«НЕ ПРИМЕНИМО» с причиной — для `AC`, который мутацией не проверить: только
ручной или не запущенный `TC`, нет изменённой строки, миграция или конфигурация.

## PLAN.md — в каком порядке делаем

| Шаг | Что меняется | Файлы | AC | TC, которые проходят после шага | Зависит от |
|-----|--------------|-------|----|---------------------------------|------------|
| 1 | вырезка даты по позиции совпадения | `<путь к файлу>` | AC-01 | TC-01, TC-02 | — |
| 2 | подсказка в поле ввода | `<путь к другому файлу>` | AC-03 | TC-05 | — |
| 3 | экран использует новую вырезку | `<путь к третьему файлу>` | AC-02 | TC-03, TC-04 | 1 |

После каждого шага проект собирается; шагов без `AC` нет. «Зависит от» —
номера шагов, которые должны быть сделаны раньше. Шаги 1 и 2 в примере можно
отдать двум исполнителям одновременно: они не зависят друг от друга и правят
разные файлы. Шаги с общим файлом выполняет один исполнитель по порядку.
Раздел «Ход работ» — чек-лист шагов (`- [x] Шаг 1`), нужен, только если нет
инструмента задач.

## REVIEW.md — журнал ревью

Запись добавляется после каждого вердикта; старые не правятся. Ревьюерам файл
не передаётся.

```text
## Ворота 3, раунд 1 — SPEC.md, ревизия 1 — 2026-11-24
<дословно из ответа ревьюера: «Проверено», вердикт, дефекты, «Дефекты
 прошлого раунда», «Ломающие входы», «Что проверить не удалось»>

Ответ исполнителя (дословно из его отчёта):
- Р1-DEF-01: исправлено в ревизии 2 — добавлен AC-05.
- Р1-DEF-02: возражаю — <причина, проверяемая по коду или документам>.
- Замечание 1: вынесено в «Не входит в задачу».

## Ворота 3, раунд 2 — SPEC.md, ревизия 2 — 2026-11-24
<дословно из ответа ревьюера>
Закрыто: Р1-DEF-01 — «устранён»; Р1-DEF-02 — «возражение принято».
```

Дефект без строки «Закрыто» в следующей записи — открытый, что бы ни ответил
исполнитель. Решение пользователя записывается его словами дословно.

У каждого дефекта ворот 10 ревьюер пишет «Должны были поймать: ворота 3 | 4 |
6 | ревью до кода | только код». По этой строке оркестратор отбирает уроки для журнала
ошибок проекта.

## INDEX.md — реестр задач

Лежит в `docs/pipeline/INDEX.md`, ведёт оркестратор. Строка на задачу:

| Задача | Дата | Размер | Статус | Название | Папка | Раунды по воротам | Дефекты по воротам | Уроков |
|--------|------|--------|--------|----------|-------|-------------------|--------------------|--------|
| PERF-3 | 2026-11-23 | M | готово | Быстрая загрузка веба | `perf-3-web-load/` | 3:1 4:1 6:2 10:1 | 3:0 4:0 6:2 10:1 | 1 |
| T-7 | 2026-11-24 | S | этап 8 | Тест просроченных задач и часовой пояс | `t-7-overdue-batch-test/` | S:1 | S:0 | — |

Статус — этап, на котором задача сейчас, «готово» или «не завершено».
«Раунды по воротам» и «Дефекты по воротам» — пары «ворота:число», при S
ревью до кода пишется как `S`. Дефекты считаются по всем раундам ворот. По
ним видно, какие ворота находят дефекты. Если размер вырос, строка остаётся
одна: меняется размер, а пары `S:…` сохраняются рядом с новыми.
Копии прошлых ревизий для повторного раунда лежат в подпапках `.rev/r<N>/`
папки задачи, N — номер раунда. Это служебные файлы, ревьюер получает только
команды сравнения.
Следующий номер для тега — на единицу больше наибольшего в реестре. Строки
не удаляются.
