# Содержимое артефактов

Файлы лежат в `docs/pipeline/<YYYY-MM-DD>-<кратко>/`, если инструкции проекта
не задают другое место. Каждый артефакт (`SPEC.md`, `DESIGN.md`, `QA.md`,
`PLAN.md`; журнал `REVIEW.md` — не артефакт) начинается с шапки:

```text
Ревизия: 1
Статус: DRAFT
```

Статус после ворот — `APPROVED (ревьюер, ревизия 1)`; для размера L до решения
человека — `APPROVED (ревьюер, ревизия 1); ждёт человека`, после —
`APPROVED (ревьюер и человек, ревизия 1)`.

Сквозные идентификаторы: `AC-NN` — критерий приёмки, `TC-NN` — тест-кейс,
`DEF-NN` — дефект из ревью. Номера `AC` и `TC` не переиспользуются; `DEF`
нумеруется внутри раунда, в журнале и запросах — с номером раунда:
`Р2-DEF-01`, для ревью S до кода — `S-DEF-01`. Пути и команды в
таблицах ниже — примеры формата.

## SPEC.md — что должно получиться

| Раздел | Содержание |
|--------|------------|
| Контекст | просьба пользователя дословно; его ответы дословно; что найдено в коде, памяти и документах; ограничения проекта |
| Размер | S, M или L и какие признаки выполняются |
| Варианты и выбор | рассмотренные решения, оценка по одним критериям, выбранный вариант, причина отказа от остальных; входы, на которых проверялась хрупкость выбранного способа |
| Соседние случаи | таблица: случай → входит или не входит → причина; у вошедших — номер `AC` |
| Требования | наблюдаемое поведение, без описания реализации |
| Критерии приёмки | список `AC-NN`; каждый проверяем тестом и однозначен |
| Не входит в задачу | что сознательно не делается, включая соседние случаи, оставленные за рамками |
| Входы из ревью | таблица: ломающий вход от ревьюера до кода → ожидаемый результат → номер `TC` либо причина, почему не входит |
| Открытые вопросы | допущения без ответа пользователя с пометкой «не подтверждено» и тем, как каждое влияет на решение |

**Размер S.** `DESIGN.md`, `QA.md` и `PLAN.md` не создаются. Их содержимое —
разделы того же `SPEC.md`: «Решение», «Тесты», «План», «Ход работ», а после
этапа 9 — «Прогон». Где скилл и шаблоны называют эти файлы, для S читай:
соответствующий раздел `SPEC.md`. До ревью раздел «Прогон»
пуст. Статус `APPROVED` при S ставится по вердикту ворот 10; до них документ
остаётся `DRAFT`.

## DESIGN.md — как это встраивается в систему

| Раздел | Содержание |
|--------|------------|
| Затронутые модули | файлы и слои, которые меняются, и кто их вызывает |
| Данные | изменения схемы, миграции, формат хранения, совместимость со старыми данными |
| Интерфейсы | новые и изменённые API, сигнатуры, события, контракты |
| Поведение при ошибках | отказы, гонки, повторы, потеря связи, граничные значения |
| Безопасность | кто имеет доступ, откуда берётся идентичность, что проверяется |
| Решения | каждое значимое решение со ссылкой на свой `AC` и отвергнутой альтернативой |

Раздел, которого задача не касается, остаётся с пометкой «не затрагивается» и
одной фразой почему.

## QA.md — как проверяем

| TC | AC | Тип | Команда или шаги | Ожидаемый результат |
|----|----|-----|------------------|---------------------|
| TC-01 | AC-01 | unit | `<команда запуска одного теста>` | «Сдать отчёт к пятнице» → заголовок «Сдать отчёт» |
| TC-02 | AC-01 | unit | тот же файл | «Сходить к врачу завтра» → «Сходить к врачу»: предлог не у даты сохраняется |
| TC-03 | AC-02 | ручной | 1) открыть экран… 2) ввести… | в списке одна запись с датой |

На каждый `AC` минимум один `TC`; негативные и граничные случаи — отдельными
`TC`; ручной тест описан шагами, которые повторит другой человек. Имя теста в
коде начинается с номера `TC`, чтобы его можно было запустить отдельно.

Раздел «Прогон» заполняется на этапе 9 и обновляется целиком после каждого
исправления:

| TC | Команда | Результат | Дата |
|----|---------|-----------|------|
| TC-01 | `<команда>` | PASS | 2026-11-24 |
| TC-07 | интеграционный, нужна тестовая БД | НЕ ЗАПУЩЕН: адрес БД не задан | 2026-11-24 |

Последней строкой — прогон тестов кода, который вызывает изменённый.

## PLAN.md — в каком порядке делаем

| Шаг | Что меняется | Файлы | AC | TC, которые проходят после шага |
|-----|--------------|-------|----|---------------------------------|
| 1 | вырезка даты по позиции совпадения | `<путь к файлу>` | AC-01 | TC-01, TC-02 |

После каждого шага проект собирается; шагов без `AC` нет. Раздел «Ход работ» —
чек-лист шагов (`- [x] Шаг 1`), нужен, только если нет инструмента задач.

## REVIEW.md — журнал ревью

Запись добавляется после каждого вердикта; старые не правятся. Ревьюерам файл
не передаётся.

```text
## Ворота 3, раунд 1 — SPEC.md, ревизия 1 — 2026-11-24
<дословно из ответа ревьюера: «Проверено», вердикт, дефекты, «Дефекты
 прошлого раунда», «Ломающие входы», «Что проверить не удалось»>

Ответ автора:
- Р1-DEF-01: исправлено в ревизии 2 — добавлен AC-05.
- Р1-DEF-02: возражаю — <причина, проверяемая по коду или документам>.
- Замечание 1: вынесено в «Не входит в задачу».

## Ворота 3, раунд 2 — SPEC.md, ревизия 2 — 2026-11-24
<дословно из ответа ревьюера>
Закрыто: Р1-DEF-01 — «устранён»; Р1-DEF-02 — «возражение принято».
```

Дефект без строки «Закрыто» в следующей записи — открытый, что бы ни ответил
автор. Решение пользователя записывается его словами дословно.
